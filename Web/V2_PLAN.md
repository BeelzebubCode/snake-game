## 1. แนวทางที่แนะนำ

สร้างแอปใหม่ใน `Web/` โดยใช้ **React + TypeScript + Phaser + Vite** ใช้ repository เดิม และเริ่มงานพัฒนาบน branch `feat/web-v2` เก็บ Python ไว้อ้างอิงจนเว็บผ่านเกณฑ์การย้าย

React เหมาะกับขอบเขตที่ต้องการเพิ่มหน้าเลือกโหมด คลังศัพท์ สถิติ และฟีเจอร์ในอนาคต ส่วน Phaser รับผิดชอบสนามเกม การวาดภาพ การเคลื่อนไหว อินพุต และเอฟเฟกต์ ทั้งสองส่วนสื่อสารผ่าน events ที่กำหนดชนิดข้อมูลไว้

ไฟล์แนบเสนอ Phaser + HTML/CSS และงูกินตัวอักษรตามโจทย์ แนวทางนั้นเหมาะกับเกมที่มีหน้า UI น้อย สำหรับ V2 นี้เลือก React เพื่อรองรับขอบเขตที่ใหญ่ขึ้น และเพิ่มการกินตามโจทย์เป็นโหมดแยกจากกติกาเดิม

### แบ่งหน้าที่ของเทคโนโลยี

| ส่วน | ทางเลือก | เหตุผลสำหรับเกมนี้ |
| --- | --- | --- |
| หน้าเว็บ | React + TypeScript | เมนู คลังศัพท์ หน้าเรียงคำ สถิติ และ settings ใช้ component ร่วมกัน |
| สนามเกม | Phaser | วาดงู ตัวอักษร ประตู อนุภาค และจัดการ scene/audio |
| กติกา | TypeScript ที่ไม่ผูกกับ renderer | ตรวจการชน ตัวอักษร คะแนน และเวลาได้โดยไม่ต้องเปิด canvas |
| Build | Vite | พัฒนาในเครื่องและสร้าง static files สำหรับขึ้นเว็บ |
| งานภาพ UI | CSS variables + CSS Modules | ใช้สี ระยะ และ motion ร่วมกัน รองรับหลายธีม |
| State ของ UI | React state/context ก่อน | ส่งเฉพาะข้อมูลที่ UI ต้องใช้ ค่อยเพิ่ม store เมื่อมีหลายหน้าที่แชร์ state จริง |
| บันทึกระยะแรก | localStorage ผ่าน SaveRepository | เก็บ settings คะแนน และ progress พร้อม schemaVersion และการจัดการข้อมูลเสีย |
| เสียงเกม | Phaser Sound Manager | ใช้ระบบเสียงของ engine; แยกกลุ่ม Music / SFX / Voice |
| เสียงศัพท์ | Web Speech API + recorded audio ในอนาคต | เริ่มจากเสียงที่เครื่องมี แล้วเพิ่มไฟล์เสียงสำหรับคำที่ต้องการคุณภาพสม่ำเสมอ |
| ตรวจสอบ | Vitest + Playwright เมื่อเริ่มเขียนแอป | ทดสอบกติกาและเส้นทางใช้งานที่เสี่ยงเกิดข้อผิดพลาด |
| ขึ้นเว็บ | GitHub Pages เป็นตัวเลือกแรก | repo อยู่ GitHub แล้ว และรุ่นแรกใช้ static hosting ได้ |

Phaser มี [template React + TypeScript ทางการ](https://github.com/phaserjs/template-react-ts) พร้อมตัวเชื่อม events ปัจจุบันหน้า [stable release](https://phaser.io/download/stable) แสดง 4.2.1 จึงเสนอเริ่มประเมิน Phaser 4.2.x ใน spike แรก ตรวจ input, scale, audio และอุปกรณ์เป้าหมายก่อนล็อกเวอร์ชันจริง เก็บ exact dependencies กับ lockfile และใช้เอกสารตรง major version

Node.js ใช้ติดตั้ง dependencies และ build บนเครื่องนักพัฒนา/CI ผู้เล่นเปิดเบราว์เซอร์ได้เลย รุ่นแรกยังไม่มี server, login หรือ cloud database; เมื่อถึงงานบัญชีและซิงก์ข้อมูลค่อยเลือกระบบหลังบ้านตามความต้องการจริง

## 2. สิ่งที่พบจาก V1

- รุ่นปัจจุบันคือ `v1.0.1` และ tag นี้ชี้ที่ HEAD ในเครื่องตอนสำรวจ
- สนาม 28 × 24 ช่อง เดินแบบกริด ค่าเริ่มต้น 10 ช่อง/วินาที งูยาว 4 ข้อ
- วงจรหลัก: เก็บตัวอักษร → เข้าประตูเขียว → เรียงเป็นคำ → ตรวจระดับศัพท์ → ได้คะแนนและคำแปล
- มี tutorial, pause, นับถอยหลัง, inventory หลายหน้า, ช่วยเรียงคำ และหยุดเมื่อสลับหน้าต่าง
- ตัวจับเวลาและการคืนอินพุตหลัง pause เป็นพฤติกรรมสำคัญที่ต้องทดสอบระหว่างย้าย
- พจนานุกรมมี 32,991 คำไม่ซ้ำ และทุกคำมีช่องคำแปลไทยที่ไม่ว่าง นี่เป็นผลตรวจโครงสร้างข้อมูล ยังไม่ได้ยืนยันความถูกต้องทุกคำ
- ไฟล์ศัพท์สองชุดรวมประมาณ 8.36 MB ก่อนบีบอัด ควรแปลงเป็นข้อมูลที่จำเป็นและโหลดชุดศัพท์ตามโหมด/ระดับ
- `data/integrate_csv_and_nectec.py` มีการประมาณระดับ CEFR จากความยาวคำ จึงต้องแยกข้อมูลที่ตรวจระดับแล้วออกจากข้อมูลที่ยังไม่ได้ตรวจ
- เสียงเดิมเป็นเสียงสังเคราะห์ใน `src/sound.py` ใช้เป็น reference ของเหตุการณ์ที่ต้องมีเสียงได้

### พฤติกรรมที่ต้องนำมาครบใน Classic

| ระบบ | ข้อกำหนด |
| --- | --- |
| งู | WASD/ลูกศร เร่งความเร็ว ห้ามกลับเข้าลำตัว ป้องกันหลาย input ใน tick เดียวทำให้กลับหลัง |
| ตัวอักษร | ใช้จำนวนจริงใน inventory เช่น APPLE ต้องมี P สองตัว |
| ประตู | ประตูเขียว ตัวคูณคะแนน ×1 และเวลารอ/เวลาหายตามกติกาเดิม |
| หมดเวลา | ลดหาง 1 ข้อ โดยเหลืออย่างน้อย 3; ตัวอักษรยังอยู่ตามพฤติกรรม V1 |
| เวลาเรียงคำ | เลือก 15/30/45 วินาที เปิด challenge แต่ละครั้งได้เวลาใหม่เต็มจำนวน |
| Pause | แช่เวลาเดินงู ประตู และ challenge; กลับแท็บแล้วรอผู้เล่นกดเล่นต่อ |
| เรียงคำ | คลิก/พิมพ์ ลบ ล้าง ช่วยเรียง เปลี่ยนหน้าตัวอักษร; ตัว P ต้องพิมพ์เป็นคำได้ |
| Tutorial | หยุดขณะอ่านคำอธิบาย หมดเวลาแล้วลองใหม่โดยไม่เสียหางหรือตัวอักษร |
| คำผัน/การสะกด | ทำตารางตัวอย่างที่รับและปฏิเสธก่อนย้าย เพราะ V1 มี stem/alias fallback |

## 3. รูปแบบเกมและลำดับฟีเจอร์

### V2.0 — เว็บที่เล่นได้ครบ

1. Classic: ย้ายเก็บอักษร/ประตู/เรียงคำให้ครบก่อนปรับสมดุล
2. หน้าเริ่มเกม เลือกระดับศัพท์ ความเร็ว และเวลาเรียงคำ
3. Tutorial ภาษาไทยและปุ่มควบคุมบนจอสำหรับมือถือ
4. คำแปล ปุ่มฟังเสียง และสรุปคำศัพท์หลังจบรอบ
5. คะแนนสูงสุด ประวัติคำที่พบ และ settings ในเครื่อง
6. ภาพเคลื่อนไหวและ SFX ครบวงจร พร้อมปิดเสียง/ลดการเคลื่อนไหว

### V2.1 — เรียนรู้และกลับมาเล่นต่อ

- Word Quest: ให้คำแปลเป็นโจทย์ แล้วเก็บตัวอักษรตามลำดับ ใช้ชุดคำที่ตรวจแล้ว
- Practice: เลือกหมวดและชุดคำ เล่นช้าและลองซ้ำได้
- สมุดคำศัพท์: ค้นหา ฟังเสียง ปักหมุด และทบทวนคำที่ผิด
- Combo, ภารกิจ, badge และ skin หลังได้ข้อมูลการเล่นเพื่อปรับสมดุล
- Daily Challenge แบบเล่นในเครื่อง แสดงให้ชัดเมื่อยังไม่มีอันดับออนไลน์
- PWA และออฟไลน์: cache ตัวเกมกับชุดคำที่ดาวน์โหลดแล้ว จัดการอัปเดต cache โดยไม่ตัดเกมกลางรอบ
- export/import progress ในเครื่อง; พิจารณา IndexedDB เมื่อประวัติเริ่มมีปริมาณมาก

### V2.2+ — เมื่อจำเป็นต้องใช้ server

บัญชีผู้เล่น ซิงก์ข้ามเครื่อง ครูสร้างชุดคำศัพท์ และ leaderboard ออกแบบฐานข้อมูล/API ในช่วงนี้ คะแนนจาก client แก้ไขได้ จึงต้องออกแบบการตรวจรอบเล่นฝั่ง server ก่อนใช้จัดอันดับจริง ส่วน multiplayer เป็นงานอีกขอบเขตหนึ่ง

### หน้าจอ

- **หน้าแรก:** เล่นต่อ/เริ่มเกม เลือกโหมด ระดับศัพท์ และปุ่มบทสอน
- **เล่นเกม:** คะแนนและพักอยู่ด้านบน สนามเป็นจุดสนใจหลัก คลังอักษรและเวลาประตูอยู่ข้างสนาม
- **เรียงคำ:** หยุดสนาม เปิดแผงมีช่องคำ ตัวอักษร เวลาที่เหลือ และปุ่มส่งคำ แสดงเหตุผลเมื่อส่งไม่ได้
- **คำตอบถูก:** คำอังกฤษ คำแปล คะแนน และปุ่มฟังเสียง จากนั้นกดไปต่อ
- **สรุปรอบ:** คะแนน จำนวนคำ รายการคำที่พบ และเล่นใหม่/ทบทวน
- **คลังศัพท์และตั้งค่า:** ใช้หน้า React ที่ค้นหา เลื่อน และใช้แป้นพิมพ์ได้สะดวก

Desktop ใช้สนามกับ sidebar สองคอลัมน์ Mobile ย้ายข้อมูลมาเหนือ/ใต้สนาม มี D-pad และ boost button ขนาดสัมผัสอย่างน้อย 44 px รักษากริด 28 × 24 สำหรับ Classic ใช้ letterbox ตามพื้นที่ ไม่เปลี่ยนจำนวนช่องกลางรอบ จำกัด scroll เฉพาะบริเวณอินพุตเกมเพื่อให้หน้าอื่นเลื่อนได้ตามปกติ

### เอฟเฟกต์ตามเหตุการณ์

| เหตุการณ์ | ภาพ | เสียงที่ออกแบบ |
| --- | --- | --- |
| เก็บอักษร | ยุบ/เด้งประมาณ 140–180 ms มีอนุภาคสั้น และ tile เข้าคลัง | soft pop สั้น ๆ มี variation เล็กน้อย |
| ประตูพร้อม | วงแหวนขยายเบา ๆ พร้อมเวลาที่อ่านได้ | chime แจ้งครั้งเดียว |
| เข้าประตู | สนามมืดลง แผงเรียงคำปรากฏประมาณ 200 ms | soft whoosh |
| คำถูก | แสดงคำ/คำแปล ตัวเลขคะแนนลอยขึ้น | success chime แล้วออกเสียงคำ |
| คำผิด | เน้น tile ที่ผิดและแสดงข้อความ | โทนต่ำสั้นและเบา |
| จบรอบ | สนามค่อย ๆ หยุด สรุปคะแนน | เสียงจบสั้น ๆ |

ไม่ต้องมีเสียงทุกก้าวของงูเพราะเกิดถี่ ระยะเอฟเฟกต์เป็นเป้าหมายเริ่มต้นสำหรับทดลองเล่น; reduced motion ตัดอนุภาค การสั่น และแสงเต้น ใช้ข้อความ/สัญลักษณ์ร่วมกับสีเสมอ จัด focus ใน modal คืน focus เมื่อปิด และมีปุ่มบนจอแทน shortcut ที่เบราว์เซอร์อาจสงวนไว้ เช่น F1/F3

## 5. เสียง

เลือก sound pack หลักหนึ่งชุดเพื่อให้เสียงเข้ากัน เริ่มทดลองจาก [Kenney Interface Sounds](https://kenney.nl/assets/interface-sounds) ซึ่งระบุ CC0 แล้วปรับระดับเสียงให้เท่ากัน เก็บที่มาและใบอนุญาตกับ asset ใน `public/audio/`

- ใช้ Phaser จัดการ SFX/เพลง ตาม [เอกสาร Audio](https://docs.phaser.io/phaser/concepts/audio)
- เริ่มเสียงหลังผู้เล่นกดปุ่มแรก เพื่อให้สอดคล้องกับข้อจำกัด autoplay ของเบราว์เซอร์
- แยก Music / SFX / Voice; ปิดเสียงทั้งหมดได้ และบันทึกค่าข้ามรอบ
- ลดเสียงเพลงขณะอ่านศัพท์ แล้วคืนระดับเดิมเมื่ออ่านจบหรือเกิดข้อผิดพลาด
- Web Speech API เลือกได้จาก [เสียงที่มีบนอุปกรณ์](https://developer.mozilla.org/en-US/docs/Web/API/SpeechSynthesis/getVoices) รอ `voiceschanged` และรองรับเครื่องที่ไม่มีเสียงอังกฤษ
- เสียง TTS อาจแตกต่างกันตามเครื่องและบางเสียงต้องออนไลน์; เล่นเกมต่อได้เมื่ออ่านเสียงไม่ได้ ไม่รับประกันเสียงศัพท์ออฟไลน์ทุกเครื่อง
- ยกเลิกเสียงอ่านค้างเมื่อเปลี่ยนคำ/ออกจากหน้า และหยุดเสียงเกมเมื่อซ่อนแท็บ

ต้นแบบใช้ Web Audio สังเคราะห์เสียงสั้นเพื่อทดสอบ อารมณ์และจังหวะ ยังไม่ได้ดาวน์โหลด sound pack หรือสร้างเพลงจริง

### ข้อตกลงระหว่าง UI และ engine

1. Core เป็นเจ้าของ game state และเวลาเพียงจุดเดียว ใช้ simulation tick คงที่ แยกจากความถี่ render
2. Phaser วาดภาพด้วย interpolation แต่ตรวจชนบนพิกัดกริด ไม่มีความจำเป็นต้องใช้ physics engine
3. React ส่ง commands เช่น `start`, `pause`, `resume`, `submitWord`; รับ events เช่น `inventoryChanged`, `challengeOpened`, `wordAccepted`, `gameOver`
4. ไม่ส่งพิกัดงูเข้า React ทุก frame; ส่งคะแนน/คลัง/สถานะเมื่อเปลี่ยน อัปเดตเวลาบน HUD เท่าที่จำเป็น
5. มี lifecycle ชัดเจน: สร้าง engine เมื่อ mount และ destroy/unsubscribe เมื่อ unmount เพื่อไม่สร้าง canvas หรือเสียงซ้ำใน React Strict Mode
6. Input มีเจ้าของตามสถานะ: ขณะพิมพ์คำ อักษร WASD/P ต้องเข้าโจทย์; input ทิศทางต้องไม่แทรกเข้าเกม
7. สถานะหลักคือ menu → countdown → playing → challenge → wordResult → countdown; paused จำสถานะเดิม ส่วน gameOver กลับ menu หรือเริ่มใหม่ได้
8. ใช้ clock กลางที่แช่เวลาเมื่อ pause/ซ่อนแท็บ เคลียร์ input เก่าตอนกลับมา ไม่เร่ง simulation ชดเชยเวลาที่ซ่อนแท็บ
9. Core ขึ้นกับ interface ของบริการเซฟ/ศัพท์ ส่วน localStorage/JSON เป็น implementation ที่เปลี่ยนเป็นระบบอื่นได้ภายหลัง

## 7. การย้ายข้อมูลคำศัพท์

นำ `data/cefr_dictionary.json` มาจับคู่ `data/en_th.json` ด้วยคำที่ normalize แล้ว สร้างรายงานจำนวนคำ คำซ้ำ คำแปลว่าง อักขระที่เกมไม่รองรับ ระดับที่ยังไม่ได้ตรวจ และความหมาย placeholder

ตัวอย่าง schema เป้าหมาย — แสดงรูปแบบข้อมูล ไม่ใช่ผลตรวจระดับศัพท์:

```json
{
  "id": "apple:noun:fruit",
  "word": "APPLE",
  "meaningTh": "แอปเปิล",
  "meaningEn": "a round fruit",
  "partOfSpeech": "noun",
  "cefr": null,
  "legacyLevel": "A1",
  "cefrStatus": "unverified",
  "categories": ["food"],
  "gameDifficulty": 1,
  "sourceIds": ["legacy-dictionary"],
  "audioUrl": null
}
```

แยก `cefr` ที่ตรวจแหล่งแล้วจาก `legacyLevel` เพื่อรักษากติกา Classic ระหว่างย้ายโดยไม่อ้างว่าระดับเดิมถูกทั้งหมด แยกความยากเกมออกจาก CEFR และคำนวณความยาวจากตัวคำ หลีกเลี่ยงเก็บค่าซ้ำที่อาจไม่ตรงกัน

เริ่มเผยแพร่ชุดคำที่ตรวจคุณภาพแล้วประมาณ 500–1,000 คำสำหรับ Word Quest/Practice แล้วค่อยขยาย ส่วน Classic ใช้ compatibility dataset ระหว่างตรวจ parity การรับคำที่เป็นคำผันต้องมีรายการตัวอย่างและนโยบายการสะกดชัดเจน ไม่ย้าย typo aliases โดยอัตโนมัติ

แต่ละ sourceId อ้างกลับไปที่แหล่งข้อมูลและเงื่อนไขการเผยแพร่ใน manifest ของชุดคำ ตรวจความหมายไทย/ชนิดคำและสิทธิ์ของแหล่งจริงก่อนรวมใน web release เพราะข้อมูลชุดเดิมมาจากหลายที่ โหลด JSON ที่เตรียมแล้วระหว่างเล่น และเตรียมดัชนีค้นหาคำ/จำนวนตัวอักษรเมื่อโหลด; เพิ่ม Web Worker เฉพาะเมื่อวัดแล้วว่าการช่วยเรียงคำทำให้เฟรมสะดุด

## 8. แผน Git และการเก็บ Python เดิม

**ใช้ repository เดิมได้ เพิ่ม V2 เป็น commit ตามปกติ** ประวัติและ release V1 ยังเป็นจุดย้อนกลับได้ `git push` ส่ง commit ขึ้น remote; การทำให้เล่นผ่าน URL ต้อง build และ deploy อีกขั้น

### ช่วงเริ่มพัฒนา

ตรวจ working tree แล้วสร้าง branch ก่อนเริ่ม implementation คำสั่งนี้เป็นแนวทาง ยังไม่ได้รัน:

```bash
git switch -c feat/web-v2
```

ตอนสำรวจมี tag `v1.0.1` ที่ HEAD อยู่แล้ว ใช้เป็น baseline ได้ เก็บ Python ณ ตำแหน่งเดิมในช่วงแรกเพื่อให้ build script และเอกสาร V1 ยังอ้าง path ถูกต้อง

แยก commit ตามงาน เช่น แผน/ต้นแบบ → scaffold → core → UI/audio → deploy ตั้ง `.gitignore` สำหรับ `Web/node_modules/`, output และรายงานทดสอบ เก็บ lockfile และ tests ของ V2 ใน Git; กฎ `/tests/` เดิมครอบคลุมเฉพาะ tests ที่ root

### ก่อน merge และ release V2

1. ผ่านเกณฑ์ V2.0 และตรวจเว็บที่ build แล้วบน preview URL
2. ปรับ `.github/workflows/build.yml`: ปัจจุบันจับ tag `v*` และระบุข้อความรุ่น Python 1.0.1 ต้องจำกัดเป็น `v1.*` หรือแยกชื่อ tag ก่อน push `v2.0.0`
3. เพิ่ม workflow ทดสอบเว็บสำหรับ PR ที่แตะ `Web/**` และ deploy เว็บจาก branch ที่ตกลงใช้จริง; build จาก `Web/` และอัปโหลด `Web/dist/`
4. เมื่อเว็บใช้งานแทนได้แล้ว ค่อยย้ายไฟล์ Python ที่ tracked เข้า `legacy/python/` ใน commit แยก ไม่ย้าย `.git`, `Web/` หรือ environment/build outputs
5. การย้าย legacy ต้องแก้ working-directory/path ของ Python build และลิงก์ README พร้อมกัน หรือระบุชัดว่าซอร์สสำหรับ build V1 อยู่ที่ tag เดิม
6. เปลี่ยน README หลักให้ชี้เว็บ V2 และมีลิงก์ release V1/legacy
7. Merge และสร้าง release V2 ตามกระบวนการของ repo โดยเก็บประวัติเดิม; ไม่ต้อง force-push หรือสร้าง repo ซ้อนใน `Web/`

ถ้าในอนาคตต้องการเหลือเฉพาะเว็บ สามารถลบ legacy ใน commit ภายหลังเมื่อยืนยันจุดอ้างอิงและ build จาก tag ได้ แต่การเริ่มย้ายวันนี้ยังไม่มีประโยชน์จากการลบต้นฉบับ

### การ deploy

ใช้ `npm ci` → typecheck/test → build → ตรวจ output → deploy static files ตาม [แนวทาง Vite](https://vite.dev/guide/static-deploy.html) สำหรับ GitHub Pages ที่ URL ลงท้าย `/snake-game/` ให้ตั้ง `base: '/snake-game/'` และโหลด asset ผ่าน base path; ถ้าเป็น custom domain ให้ตั้งตาม URL จริง อย่านำ `vite preview` มาใช้เป็น production server

### การตรวจสอบที่ต้องมีเมื่อเริ่มแอปจริง

- Unit tests: กลับทิศ การชน/ช่องหางที่กำลังย้าย ตัวอักษรซ้ำ การใช้ inventory ระดับคำ คะแนน และ deadline
- State tests: หมดเวลาขณะ pause ซ่อนแท็บระหว่าง challenge tutorial retry และเสียง/อินพุตค้างหลัง restart
- Browser tests: เริ่ม → เก็บ → เข้าประตู → พิมพ์/คลิก → ส่ง → ไปต่อ → จบ → เล่นใหม่ และเรียกเมนูด้วย keyboard
- Persistence: อ่าน save รุ่นเก่า/เสีย/เขียนไม่ได้แล้วเล่นต่อได้ แจ้งกรณี progress บันทึกไม่ได้; localStorage เป็นข้อมูลของเบราว์เซอร์นั้น ไม่ซิงก์ข้ามเครื่อง
- ภาพ/การใช้จริง: desktop Chrome/Firefox/Safari, Android Chrome, iPhone Safari; จอแนวตั้ง/แนวนอน ปุ่มสัมผัส ฟอนต์ไทย และการเปลี่ยนขนาด
- ประสิทธิภาพ: ตั้งเป้า render 60 fps บนอุปกรณ์ทดสอบที่ระบุ วัดเฟรมช่วง particles และ hint search ลดเอฟเฟกต์บนเครื่องที่ไม่ไหว โดยคงความเร็ว simulation
- Release: production build เปิดผ่าน subpath จริง โหลดข้อมูล/ฟอนต์/เสียงครบ ไม่มี console error และตรวจว่า V2 tag ไม่เรียก Python release
